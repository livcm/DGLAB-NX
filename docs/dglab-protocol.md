# DG-LAB Protocol

本文记录本项目对 DG-LAB 蓝牙协议的移植范围、实现位置与验证状态。

本文的 Coyote V3 属于 **BLE 模式**（sysmodule 直接连接 DG-LAB 设备，**未实现、已搁置**）；
其中的编解码（B0/BF/B1 与波形频率换算）被现行 **WebSocket 模式**复用，见
`docs/dglab-socket.md` 与 `docs/ipc.md` 的 `NET_WAVEFORM`。

蓝牙协议的代号是 **Coyote**（V2 / V3）。它与 Socket 协议的 V3 / V4 是两条独立的协议线，
版本号没有对应关系：Socket 那条见 `docs/dglab-socket.md`。

## 支持的设备与协议版本

| 项目 | 值 |
| --- | --- |
| 设备 | 郊狼情趣脉冲主机 3.0 |
| 设备蓝牙名称 | `47L121000` |
| 协议版本 | Coyote V3 |
| V2 支持 | 未实现，也不计划与 V3 混在同一层实现 |

V3 与 V2 的数据格式不同：V3 无需大小端转换，强度范围为 0~200，波形强度范围为
0~100，波形频率以 10~240 的设备值发送。禁止把 V2 的 X/Y/Z 数据格式套用到 V3。

## BLE 特性

基础 UUID：`0000xxxx-0000-1000-8000-00805f9b34fb`。

| 服务 | 特性 | 属性 | 用途 | 长度 |
| --- | --- | --- | --- | --- |
| `0x180C` | `0x150A` | 写 | 所有指令写入 | 最长 20 字节 |
| `0x180C` | `0x150B` | 通知 | 所有回应消息 | 最长 20 字节 |
| `0x180A` | `0x1500` | 读 / 通知 | 电量 | 1 字节 |

这些 16-bit UUID 在 `DGLAB_COYOTE_V3_UUID16_*` 中定义，传输层不得另行推导。

## 指令

### B0：通道强度 + 波形数据（20 字节，每 100ms 一次）

```
0xB0 | 序列号(4bits)+强度值解读方式(4bits) | A 强度设定值 | B 强度设定值
     | A 波形频率 x4 | A 波形强度 x4 | B 波形频率 x4 | B 波形强度 x4
```

- 强度值解读方式：高 2 bits 为 A 通道，低 2 bits 为 B 通道。
  `0b00` 不改变、`0b01` 相对增加、`0b10` 相对减少、`0b11` 绝对设置。
- 强度设定值有效范围 0~200；范围外的输入被设备当作 0 处理。
- 波形频率 4 组有效范围 10~240，波形强度 4 组有效范围 0~100，
  每组覆盖 25ms，4 组合计 100ms。
- 某通道的 4 组数据中只要有一个值超出有效范围，设备会放弃该通道全部 4 组数据。
  这也是官方文档给出的“只驱动单通道”做法。
- 序列号 0 表示不需要设备回应通道强度；非 0 时设备通过 B1 返回相同序列号。
  官方建议：序列号非 0 时，等收到相同序列号的 B1 之后再修改强度。

### BF：软上限与平衡参数（7 字节）

```
0xBF | A 强度软上限 | B 强度软上限 | A 频率平衡参数 | B 频率平衡参数 | A 强度平衡参数 | B 强度平衡参数
```

- 软上限有效范围 0~200，范围外的输入不会修改当前软上限（注意与 B0 的
  “范围外按 0 处理” 语义不同）。
- 软上限与平衡参数均断电保存，但 BF 立即生效且没有返回值，
  官方要求每次重连后重新写入 BF。

### B1：强度回应（4 字节，通知）

```
0xB1 | 序列号 | A 通道当前实际强度 | B 通道当前实际强度
```

设备在强度变化时立即返回。由 B0 引起的变化会带回对应的序列号，
其他来源（例如拨动滚轮）的序列号为 0。

`BE` 消息在官方文档中已标记为弃用，本项目不实现。

### 波形频率换算

程序侧可以暴露 10~1000 的波形频率（单位 ms），发送前按官方算法压缩：

```
10..100   -> value
101..600  -> (value - 100) / 5 + 100
601..1000 -> (value - 600) / 10 + 200
否则       -> 10
```

## 本项目实现

协议层保持平台无关（只依赖 C 标准库，不包含 libnx / HOS 头文件），
以便在电脑上直接测试。实现分为三层：

| 内容 | 位置 |
| --- | --- |
| 编解码 | `sysmodule/include/dglab/protocol/coyote_v3.h`、`sysmodule/source/protocol/coyote_v3.c` |
| 强度状态机 | `sysmodule/include/dglab/protocol/coyote_v3_strength.h`、`sysmodule/source/protocol/coyote_v3_strength.c` |
| 设备会话 | `sysmodule/include/dglab/protocol/coyote_v3_session.h`、`sysmodule/source/protocol/coyote_v3_session.c` |
| 主机侧测试 | `tests/protocol/` |

职责划分：

- 编解码层：B0 / BF / B1 的字节布局、波形频率换算、波形槽有效性与整通道丢弃规则；
- 强度状态机：累积用户输入、分配序列号、等待 B1 的闸门、绝对归零；
- 会话层：100ms 节拍、连接生命周期、重连重写 BF、波形播放与分组填充。

会话层不直接调用 BLE：它通过 `DglabCoyoteV3Link` 回调写出字节，时间由外部调用
`dglabCoyoteV3SessionTick()` 提供。Sysmodule 之后只需要把回调接到 BLE transport、
把 tick 接到自己的线程或定时器；主机测试则接一个记录器。

### 会话层行为

- 连接建立后立即写 BF，且一定早于任何 B0，保证软上限已知；
- 连接期间每 100ms 写一条 B0；单次 tick 最多写一条，调用方迟到不会造成突发写入，
  小于 100ms 的余量会保留以维持相位；
- 断开时清空未完成状态（在途强度、闸门、播放位置、tick 余量），
  波形内容与 BF 参数保留给下次连接；
- 波形按 4 组一包发送并循环，每轮循环对齐到包边界；
- 未设置波形的通道写入全 0 槽位（频率 0 越界），设备丢弃该通道数据，
  另一通道继续播放。

### 强度写入策略

`DglabCoyoteV3StrengthFeedback` 对应官方文档中的两种写法：

- `Required`（默认值）：累积变化 → 用非 0 序列号写入 → 等待相同序列号的 B1 →
  才允许下一次强度写入。等待期间用户输入继续累积，不会丢失；
- `None`：始终用序列号 0 写入，不等待 B1，对应文档中"不需要设备反馈"的场景。

其他规则：累积值钳制在 ±200；序列号在 1~15 之间循环，0 保留；
绝对归零请求覆盖同通道尚未发送的累积值，并且同样要等闸门打开。

运行主机侧测试：

```
make -C tests/protocol
```

`sysmodule/Makefile` 的 `SOURCES` 同时包含 `source/protocol`，
因此同一份代码也会在 devkitA64 下编译。

## 验证状态

已在电脑上验证（`make -C tests/protocol`，3 个测试程序共 363 项检查，全部通过）：

- 编解码：B0/BF 编码与解码、B1 解码，含错误 header、长度不足与多余字节；
- B0 报文与官方文档 4 个例子的 6 条报文逐字节比对，含单通道与双通道场景；
- 序列号 4 bits 与强度解读方式的位打包；
- 波形频率换算表，含三分支边界与范围外回退到 10；
- 波形槽有效性、整通道丢弃规则、通道置空闲；
- 强度状态机：官方时序（累积 → 带序列号发送 → 闸门关闭期间继续累积 → B1 放行 →
  发送累积值）、相对减少、A/B 两通道混装共用序列号、序列号 0 与过期序列号不放行、
  绝对归零、归零请求等待闸门、序列号 15 回绕到 1、累积值钳制、即发即忘模式；
- 会话层：每次连接后重写 BF、100ms 节拍与余量保持、迟到 tick 不补发、
  断开期间忽略输入与 tick、断开丢弃在途强度、典型 B0 报文逐字节比对、
  波形循环与包边界对齐填充、清除波形后转空闲、非 B1 通知被忽略；
- 编码不会写出目标缓冲区之外。

测试本身也做过有效性确认：人为改坏一个期望字节后测试会失败并打印实际/期望数据，
改动已还原。

尚未验证（需要 Switch 实机与真实设备）：

- BLE 传输行为（扫描、连接、MTU、写入与通知）尚未实现；
- BF 写入的实际生效与断电保存；
- B1 的实际返回时序；
- 软上限对 B0 绝对/相对强度的实际钳制；
- “通道置空闲”使用频率 0 是否与官方示例中的强度 101 完全等价；
- 100ms 节拍在实机线程调度下的抖动。

## 与官方文档的差异、冲突与实现选择

以下各点均已确认过两种写法，但没有为了"看起来一致"而隐藏：

1. 序列号是包级而非通道级。官方参考代码以 A 通道为例，按通道维护 `orderNo`，
   但 B0 只有 1 个序列号字段、B1 也只回 1 个序列号。本项目使用一个共享计数器与
   一个共享闸门，两个通道的强度变化合并进同一条 B0。该选择已被测试固定。
2. `coyote/README.md` 的 650ms → 204 与 `coyote/v3/README.md` 的换算算法
   （650 → 205）冲突。当前实现采用 V3 协议文档中的算法，待实机确认。
3. 波形补齐：`coyote/README.md` 描述为"4 个一组，不足的 0 补"，但频率 0 超出
   10~240 有效范围，会让设备丢弃该通道整包数据，连前面有效的几组也一起失效。
   本项目改为"沿用最后一个频率 + 强度 0"补齐，效果是静音但数据仍然有效。
4. 文档未规定的会话层策略（属本项目选择，非协议要求）：
   tick 迟到不补发、波形循环对齐包边界、绝对归零覆盖同通道已累积值、
   累积值钳制在 ±200。

## 已知限制与后续工作

本节只管 **BLE 模式**（Coyote V3）。现行的 **WebSocket 模式**见 `docs/dglab-socket.md`，
它只复用本文的编解码，不用会话层——不要把这里的待办当成 WebSocket 模式的待办。

- BLE transport 目前只有 PoC（扫描、连接、服务发现、读写、通知），见
  `docs/ble-poc.md`；它尚未接入本文件的协议会话层，写的还是固定报文；
- 会话层（`dglabCoyoteV3SessionTick()`）目前只被主机测试驱动：它按 BLE 的 100ms
  节拍设计，而 WebSocket 模式是"事件源上传槽位 + 服务端按需补流"，两者节奏模型不同，
  所以会话层随 BLE 模式一并搁置，不是 WebSocket 模式的待办；
- 会话层的时间目前由测试以虚拟时间提供，尚未与真实 100ms 定时源结合；
- 电量读取只在 PoC 里通过临时 IPC 命令触发，尚未进入正式接口；
- 尚未实现 V2 协议；
- 稳定 IPC 面向的是 WebSocket 模式：`GET_VERSION` / `PING` 与 `NET_*`（启动/停止、
  状态、二维码、强度、清空、波形上传），见 `docs/ipc.md`；BLE 连接相关的命令只在
  临时的 `common/include/dglab/ipc_poc.h` 里，随 BLE 模式搁置。
